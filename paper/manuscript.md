## 1. 서 론

LLM 에이전트는 오래 쓸수록 기억할 내용이 문맥 길이를 넘으므로 기록을 **반복해서 압축**한다. Hermes Agent[1]에는 두 가지 반복 압축이 있다.
① 영구 메모리 MEMORY.md는 2,200자로 제한되고 자동 압축되지 않아, 한도를 넘으면 메모리 도구가 오류를 돌려주고 LLM이 세션마다 항목을 합치거나 지운다.
② 긴 대화는 오래된 부분을 요약하고, 다음 압축 때에는 **이전 요약에 새 대화를 덧붙여 다시 요약**한다. 두 경우 모두 LLM이 자기가 쓴 요약을 다시 고쳐
쓰므로, 한 번 빠지거나 왜곡된 정보는 복구되지 않는다.

손실은 단순히 길이만의 문제가 아니다. 설정은 바뀌고(8080→9090), 특정 범위에만 예외가 있으며(staging만 8081), 검토 후 기각된 값도 기록에 남는다.
압축 중에 옛 값이 현재값처럼 남거나 예외가 기본값을 덮으면 **틀린 기억**이 된다. Hermes는 모델이 여러 사실이 든 항목을 통째로 덮어쓰는 문제로
`replace` 동작을 없앴고, 30B 미만 모델은 메모리 도구를 잘 쓰지 못한다고 안내한다[1]. 그러나 우리가 아는 한, 개인이 소형 로컬 모델로 에이전트를 쓸 때
반복 압축에서 정보가 얼마나, 어떤 종류부터 사라지는지를 실제 배포 코드로 측정한 연구는 없다.

기여는 다음과 같다. (1) Hermes의 실제 메모리 도구와 문맥 압축기를 4·9B 로컬 모델로 구동해, 정답이 알려진 기록에서 손실을 누락·버전 혼동·범위 혼동
등 유형별로, 그리고 세션 진행과 압축 횟수(1·3·5·10회)에 따라 측정한다. (2) LLM에게는 사실 추출만 맡기고 병합·압축은 결정적 규칙으로 하는
**CEM**(Change- and Exception-aware Memory)을 Hermes 항목 형식 그대로 적용하고, 형식·병합·추출의 기여를 제거 실험으로 분리한다. (3) CEM이 같은 예산에서
정답률을 높이고 틀린 값 응답을 줄이며, 원장을 다시 렌더링하는 구조이므로 반복 압축에서도 손실이 쌓이지 않음을 확인한다.

## 2. 관련 연구

MemGPT[2]는 LLM이 스스로 메모리를 관리하는 계층 구조를 제안했고 Hermes의 자기 편집형 메모리도 이 계열이다. Mem0[3]는 추출한 사실마다 LLM이
ADD/UPDATE/DELETE를 고르고, Zep[4]은 유효 구간을 가진 시간 지식 그래프로 옛 사실을 무효화한다. LongMemEval[5]은 지식 갱신·시간 추론·답변 보류를
평가 축으로 제시했다. 최근 제한된 자기 관리 메모리에서 갱신 정보가 소실되고[6], 반복 통합이 기억을 오염시키며[7], 요약에서 조건(범위)이 탈락하고[8],
반복 압축으로 규칙이 급격히 사라짐[11]이 보고되었다. 이에 대해 근거 추출과 결정적 갱신 규칙을 분리하는 접근[9,10]이 제안되었고, 표현 형식만으로 성능 차가
생길 수 있다는 지적[12]도 있다. 본 연구의 LLM 병합 제거 실험은 Mem0식 LLM 병합을, (엔티티, 속성, 범위) 버전 사슬은 Zep의 유효 구간 무효화를 글자 예산
메모리에 맞춘 것이다. [9,10]이 검색 후 조립 단계를 다룬다면, CEM은 고정 2,200자 메모리 본문 자체를 결정적으로 구성하고 한계 글자비용 탐욕 배치로 예산을
지킨다. 기존 연구는 주로 검색형 메모리와 대형 모델을 다루며, 배포 에이전트의 고정 예산 메모리와 반복 문맥 압축을 소형 로컬 모델로 운용할 때의 손실을
버전·범위·압축 횟수 축에서 함께 측정하지 않았다. 본 연구는 새로운 메모리 구조가 아니라 이 진단과 추출–결정적 병합 분리의 Hermes 호환 적용에 초점을 둔다.

## 3. 제안 방법: CEM

그림 1은 Hermes 기본 방식과 CEM을 비교한다. **① 사실 추출(LLM)**: 세션 메모마다 (엔티티, 속성, 범위, 값, 이전값)을 JSON 스키마 제약 출력으로 뽑는다.
지금까지의 엔티티·속성 이름을 함께 주어 같은 대상을 같은 이름으로 부르게 하고, 범위 신호어(except, only, overrides 등)와 "검토만 한 값은 설정이 아님"을
지시한다. **② 근거 검증**: 값이 원문에 그대로 없으면 버린다(예: "keeps its usual length"에서 `usual`을 값으로 뽑는 오류 제거). **③ 결정적 병합**: 이름을
정규화(대소문자·`_`/`-`·문장부호, 퍼지 매칭)해 (엔티티, 속성, 범위) 키를 만들고 키마다 시간순 버전 사슬을 유지한다. 같은 값의 재확인은 새 버전이 아니며,
관측된 이력이 있으면 LLM이 적은 이전값보다 이력을 우선한다. 예외는 별도 키라서 기본값을 덮을 수 없다. **④ 예산 배치**: 엔티티당 Hermes 항목 하나
(`Orion: API port 9090 (was 8080; staging: 8081)`)로 렌더링하고, 추가 글자 비용이 가장 작은 사실부터 넣어 B자 안의 보존 사실 수를 최대화한다(동률 시
현재값>예외>이전값, 최근 갱신 우선). LLM은 세션 메모에서 사실을 한 번만 뽑고 메모리 본문을 다시 쓰지 않는다. 전체 원장은 보관 파일로 저장해 매번 같은
규칙으로 렌더링하므로, 결과가 압축 횟수와 무관함이 **설계상 보장**된다(대신 원장 파일을 따로 저장한다).

## 4. 실험 설계

**데이터.** 영어 템플릿으로 정답이 알려진 합성 메모 기록을 만든다. 엔티티(서비스·호스트·팀) 24개 × 속성 3개에 대해 변경 50%(일부 2회·되돌림), 범위 예외 35%,
재확인 30%, 기각 제안 12%를 날짜별 메모 파일 37~49개(노트 167~205개, 원문 1.0~1.3만 자)로 섞고, 30%는 속성 동의어로 쓴다. 값은 에피소드 안에서 유일해
오답의 출처(옛 버전·다른 범위·기각값 등)를 자동 판정한다. 질문은 7유형이다: 현재값(CUR, 바뀐 설정의 최신값), 불변값(STABLE), 직전값(PREV, 마지막 변경 직전 값),
예외값(EXC), 예외 없음(EXCNEG, 예외가 없는 범위를 물으며 정답은 기본값), 교훈 메모(NOTE), 모름(ABSTAIN, 기록된 적 없는 속성). 독립 에피소드 3개(시드 1~3)에서
475개이며, 같은 모델이 메모리만 보고 답하고 정답 값과 일치해야 정답이다. **전체 정확도**는 문항 평균, **매크로 정확도**는 7유형 정확도의 단순 평균(유형별
12~109문항)이며, **오답률**은 답이 존재하는 질문(ABSTAIN 제외) 가운데 '모름'이 아닌 틀린 값을 답한 비율이다('모름'이 많으면 낮아지므로 정확도와 함께 읽는다).

**실험 1 (2,200자 메모리).** 모든 방법은 같은 모델·온도 0·Hermes 글자 수 계산(항목을 `\n§\n`로 이은 길이 ≤ 2,200)을 쓴다. 최신 노트 유지, Hermes 무통합(가득
차면 추가 거부), LLM 요약, 구조화 요약(CEM과 같은 출력 형식), Hermes 에이전트(실제 `memory` 도구 스키마·지침·세션별 고정 스냅샷, 초과 시 Hermes 오류로 통합
유도)와 그 JSON 강제 변형을 비교하고, 원문을 보관하는 참조선으로 무압축 원문과 질문 시점 BM25 검색을 둔다. LLM 방법에는 평가 대상(현재값·예외·직전값)을
알리는 같은 안내 문장을 주었다. 제거 실험은 이전값 보존 제거, 범위 키 제거, 같은 추출 결과의 LLM 병합(Mem0식), 정답 추출(Oracle)이다.

**실험 2 (반복 문맥 압축).** Hermes `ContextCompressor`의 실제 요약 프롬프트를 import해 쓴다. 기록을 시간순으로 k개(1·3·5·10) 구간으로 나누어, i번째 압축에서는
(i−1번째 요약 + i번째 구간)을 Hermes 갱신 프롬프트로 요약한다(요약본만 재압축). 비교 대상은 원본 참조 재압축(매번 원문 전체를 새로 요약; 최종 요약은 k=1과 같고
입력 토큰은 k에 비례, k=1 실측으로 추정)과 CEM 원장(글자 제한 없이 전체 원장)이다. 요약 예산은 Hermes 기본값(2,000토큰), FOCUS TOPIC 기능에 같은 안내 문장을
넣었고, 탐욕 디코딩에서 4B가 반복 루프에 빠져 요약기에만 Qwen3.5의 Ollama 기본값 presence_penalty 1.5를 적용했다.

**환경.** RTX 3060 12GB, Ollama 0.32.5, qwen3.5:9b(Q4_K_M, 주 모델)·qwen3.5:4b, thinking 비활성. Hermes Agent 커밋 67481b6의 `memory_tool`·`MemoryStore`·
메모리 지침·`ContextCompressor`를 수정 없이 import했다(전체 에이전트 루프는 64K 문맥 요구로 제외). 질문 단위 McNemar 검정(Holm 보정)과 (시드, 엔티티) 군집
부트스트랩 95% 신뢰구간을 쓴다.

## 5. 실험 결과

### 5.1 실험 1: 2,200자 메모리 (표 1)
9B에서 CEM의 전체 정확도는 64.0%로 LLM 요약(51.4%), 구조화 요약(56.4%), Hermes 에이전트(도구 30.3%, JSON 34.7%), 최신 노트 유지(25.7%), Hermes 무통합(23.6%)보다
높았다. 매크로 정확도 차이는 LLM 요약 대비 +10.5%p[95% CI +2.4, +18.4], 구조화 요약 대비 +9.9%p[+1.9, +17.7], Hermes 에이전트 대비 +24.2%p였고, 질문 단위
McNemar 검정(Holm 보정)에서도 각각 p=0.0002, 0.035, <10⁻²⁵로 유의했다. CEM의 오답률은 7.3%로, 정답률이 비슷하거나 더 높은 요약(16.9%)·구조화 요약(17.8%)·
무압축 원문(17.8%)의 절반 이하였다(정답률이 낮은 LLM 병합 5.2%, Hermes 에이전트 8.9%는 누락이 많아 오답률이 낮다). 같은 9B 모델이 원문 전체(질문당 약 5,600토큰)를
읽고도 직전값은 46.8%만 맞혀(버전 혼동 13.9%) 이전값을 명시한 CEM(59.6%, 약 1,170토큰)보다 낮았다. 반면 예산에 다 담지 못한 현재값·예외값은 원문(93.5%, 87.2%)보다
낮았고(70.8%, 50.0%), 원문을 보관하는 무압축 원문·BM25(약 78%)가 2,200자 메모리의 상한 역할을 했다. 같은 출력 형식으로 LLM이 직접 요약한 구조화 요약보다 높으므로
이득은 형식만으로 설명되지 않는다. 4B에서도 전체 정확도는 CEM 64.0%로 요약 58.7%, 구조화 요약 56.4%, Hermes 에이전트 43.8%보다 높았다(매크로는 요약과 비슷: 60.5% 대 59.3%).
개발에 쓰지 않은 시드 2–3만 보아도 전체 정확도는 CEM이 가장 높았다(9B 62.7% 대 요약 47.1%·구조화 58.1%, 4B 64.8% 대 59.6%·56.9%).

### 5.2 손실의 종류와 진행 (그림 2·3)
최신 노트 유지·Hermes 계열의 오류는 대부분 **누락**(50~64%)이었고, LLM 요약 계열은 누락은 적지만 **버전 혼동(9.9~10.5%)과 범위 혼동(4.4~5.7%)**이 많았다. CEM은 버전
혼동 4.2%, 범위 혼동 2.1%로 요약 계열의 절반 이하였고 남은 오류는 주로 예산 부족에 따른 누락이다. 유효 사실(그 시점의 현재 기본값과 예외값)의 보존율(정답 값이 해당
엔티티 항목 안에 남은 비율)은 Hermes 에이전트에서 세션 진행 50% 시점에 58%, 끝에는 30%로 떨어졌고(그림 3), 한 세션에서 최대 970~1,437자가 한꺼번에 삭제되었다.
도구 호출 244회 중 123회(50%)가 실패했고, 출력을 JSON으로 강제해 형식 오류를 없애도 용량 초과·필수 필드 누락으로 호출의 49%가 실패하며 정답률은 34.7%에 그쳐,
소형 모델의 통합 정책 자체가 손실 원인으로 보인다. CEM은 끝까지 71%를 보존했다(정답 추출 Oracle 74%).

### 5.3 제거 실험 (표 1 하단)
같은 추출 결과를 LLM이 병합하면(Mem0식) 정답률이 27.6%로 떨어졌다. LLM 병합본은 예산으로 자르기 전에도 사실의 68~85%(4B 34~47%)만 담으면서 4.4~5.8천 자로 예산을
넘겨 잘려 나갔지만, 결정적 병합은 3.4~3.9천 자에 95~98%를 담았다. 범위 키를 빼면 범위 혼동이 2.1%→14.9%로 늘고 전체 정확도가 57.9%로 떨어졌다(예외 없는 범위
질문에서만은 오히려 유리해 매크로는 62.6%). 이전값 보존을 빼면 직전값 정확도가 59.6%→1.8%로 떨어지는 대신 현재값은 70.8%→80.6%로 올라, 예산 안에서 이전값과 현재값이
자리를 다툼을 보였다. Oracle과의 전체 정확도 차이는 4.0%p(p=0.07)였고, 추출의 값 재현율 99.3~100%, 범위 일치율 98.4~100%, 기각값 유입 0건이었다. 남은 약점은
동의어로, 동의어로 기록된 키의 정확도(58.9%)가 기본 키(67.1%)보다 낮았다.

### 5.4 실험 2: 반복 문맥 압축 (그림 4)
Hermes 압축기로 같은 기록을 k번에 나누어 압축하면 정답률이 4B(시드 1–3)는 k=1·3·5·10에서 62.1·62.5·54.7·45.1%, 9B(시드 1–3)는
68.2·69.5·60.2·52.2%로, k=3까지는 k=1과 비슷했고 그 뒤 떨어졌다. 원본 참조 재압축은 매번 원문 전체를 새로 요약하므로 정확도는 k=1과 같고 입력 토큰도 요약본 재압축보다 적다
(k=10 추정 약 3.1만 대 실측 4.4~4.5만). 그러나 원문 전체를 보관하고 매번 문맥에 넣어야 하므로, 원문이 문맥 창을 넘는 상황—즉 문맥 압축이 필요한 바로 그 상황—에서는
쓸 수 없다. CEM 원장은 설계상 k와 무관하며 4B 81.1%, 9B 78.7%였고, 길이는 약 3.5천 자로 Hermes 요약(8.5~9.5천 자)의 40% 수준이었다.
CEM은 k=1에서도 이미 Hermes 요약보다 10.5~19.0%p 높았으므로, k=10에서 벌어진 차이(26.5~36.0%p) 가운데 반복 압축에 따른 누적 손실 몫은 16.0~17.0%p이다.
정보 유형별로 보면 반복할수록 9B는 **예외 조건**(74.4% → 24.4%), 4B는 **현재 설정값**(80.6% → 41.8%)이 크게 무너졌다. **변경 이력**은 9B 요약에 옛 값이
82~89% 남아 있었지만 정답률은 39~50%에 그쳐, 남은 값이 직전 값인지 구별하지 못하는 읽기 손실이 컸다. CEM은 세션당 한 번 추출하며(누적 입력 약
2.8~2.9만 토큰, k=5~10 반복 압축과 비슷) 원문 전체를 다시 읽지 않는다.

### 5.5 예산에 따른 변화 (9B, 시드 1, 148문항)
예산 1,100·2,200·4,400자에서 CEM의 매크로 정확도는 41.2·59.0·71.0%로 LLM 요약(37.8·52.9·54.7%)·구조화 요약(33.4·45.7·55.9%)·Hermes 에이전트(24.4·46.8·53.9%)보다
모든 예산에서 높았고, 요약 계열과의 차이는 예산이 클수록 커졌다(LLM 요약 대비 +3.4→+6.1→+16.3%p). 4,400자에서는 CEM이 사실을 거의 모두 담아 전체 정확도 84.5%로
원문 전체(약 1.0만 자)를 넣은 무압축 원문(79.7%)보다 높았고, 1,100자(원문의 약 1/10)에서는 전체 정확도가 LLM 요약과 비슷했다(39.2% 대 41.2%).
범위 키 제거 변형은 매크로로는 CEM과 비슷했으나(47.8·58.7·71.4%) 예외 없는 범위 질문에서만 유리했기 때문이며, 전체 정확도는 모든 예산에서 CEM보다 낮았다(37.8·60.1·71.6% 대 39.2·66.9·84.5%).

## 6. 결 론

Hermes Agent의 두 반복 압축—2,200자 메모리의 자기 통합과 이전 요약을 다시 고쳐 쓰는 문맥 압축—을 소형 로컬 LLM으로 운용하면, 자기 통합은 대량 삭제로 유효 사실의
대부분을 잃고, LLM 요약은 직전 값과 예외를 먼저 잃거나 혼동하며, 압축을 반복할수록 예외 조건과 현재 설정값까지 손실이 쌓였다. LLM의 역할을 사실 추출로 제한하고
병합·압축을 (엔티티, 속성, 범위) 키 기반 결정적 규칙으로 바꾼 CEM은 같은 예산에서 정답률을 높이고 틀린 값 응답을 절반 이하로 줄였으며, 원장을 다시 렌더링하므로
반복 압축에도 성능이 유지되었다.

**한계.** (1) 데이터는 영어 템플릿으로 만든 합성 메모(엔티티 24개, 에피소드 3개)이며, 99% 이상의 추출 재현율은 정형화된 문장 덕일 수 있다. (2) Qwen3.5 4B·9B 두
모델로 메모리·압축 하위 시스템만 실측했고 전체 에이전트 루프는 다루지 않았다. (3) 예산 변화는 시드 1(148문항)만 수행했다. (4) CEM의
이름 정규화와 추출 프롬프트는 시드 1 결과를 보고 수정한 뒤 시드 1–3을 모두 다시 실행했으며, 개발에 쓰지 않은 시드 2–3만 보아도 CEM이 가장 높았다. (5) 원문을
보관하고 질문마다 읽는 무압축 원문·BM25(약 78%)는 CEM보다 높다. (6) 예외가 없는 범위를 물으면 대부분의 방법이 기본값 대신 '모름'으로 답했고(CEM 33.3%, 무압축 원문
25.0%), 동의어 키 분할이 남은 약점이다(LLM으로 동의어를 묶는 시도는 9B가 과병합하거나 전혀 묶지 못해 채택하지 않음). 알려진 구현 한계(배치 단계 구분자 비용 누락,
단위 표기만 다른 재확인을 새 버전으로 처리)는 모두 CEM에 불리한 방향이다. 향후 실제 사용 로그와 한국어 메모, 동의어 정규화를 다룰 계획이다.
