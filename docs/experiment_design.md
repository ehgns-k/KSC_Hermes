## 1. 연구 질문
- **RQ1 (진단)**: Hermes Agent의 2,200자 MEMORY.md를 소형 로컬 LLM(≤9B, RTX 3060)이 스스로 통합할 때, 어떤 정보가 어떤 방식으로 손실되는가? (누락인가, 버전·범위 혼동인가)
- **RQ2 (방법)**: LLM에게는 원자적 사실 추출만 맡기고, 병합·압축은 (엔티티, 속성, 범위) 키 기반의 결정적 규칙으로 수행하면(CEM), 같은 글자 예산에서 정보 손실이 줄어드는가?
- **RQ3 (조건)**: 그 효과는 예산(B)과 원문 규모(E), 모델에 따라 어떻게 달라지는가? 남은 손실은 추출 단계에서 생기는가, 예산(저장) 단계에서 생기는가?

## 2. 데이터: 합성 "메모리 스트림" (정답이 정확히 알려진 벤치마크)
- 한 에피소드 = 수개월 동안의 Hermes 세션에서 남은 **날짜별 메모 파일** 수십 개 (`memory/2026-01-05.md` …).
- 엔티티 E개(서비스·호스트·팀) × 속성 3개. 각 (엔티티, 속성)에 대해
  - 초기값 1회, 50% 확률로 변경(그 중 25%는 2회 변경, 2회째의 25%는 **이전 값으로 되돌림**),
  - 35% 확률로 **범위 예외**(staging, EU region, 주말 실행 등),
  - 30% 확률로 현재값 재확인(중복), 12% 확률로 **검토 후 기각된 값**("…로 바꾸려 했으나 유지").
- 표현 다양화: 노트 템플릿(초기 8, 변경 10, 예외 5, 재확인 5, 기각 3, 되돌림 2), 30% 확률로 **속성 동의어**("API port"→"listen port").
  변경 노트의 절반만 이전 값을 명시한다.
- 자유 형식 교훈 노트(NOTE, 예: "사무실 VPN은 MTU 4656에서만 동작")와 일반 선호 노트(방해 요소) 포함.
- 모든 값 토큰은 에피소드 내에서 유일 → 오답이 어디서 왔는지(옛 버전, 다른 범위, 다른 속성, 다른 엔티티, 기각값, 원문에 없음) 자동 판정.
- Hermes 보안 스캐너(`_scan_memory_content`)에 걸리는 노트가 없음을 확인(시드 0–3, E=12/24/48에서 0건).
- 규모: E=24 → 노트 약 170–200개, 원문 약 10–12.5천 자(2,200자 예산의 약 5–6배).

보관(archive)된 사실은 QA 때 보이지 않는다.

## 4. 제안 방법: CEM (Change- and Exception-aware Memory)
1. **추출(LLM)**: 세션 파일 단위로 (note, entity, attribute, scope, value, previous_value)를 JSON 스키마 제약 출력으로 추출.
   기존 엔티티·속성 목록을 프롬프트에 주어 이름 재사용을 유도.
2. **근거 검증(결정적)**: 값이 원문 노트에 그대로 나타나지 않으면 버림("usual", "unchanged" 같은 비값 제거). 이전 값은 기본 범위에서만 사용.
3. **키 정규화·병합(결정적)**: 이름 정규화 + 퍼지 매칭으로 (엔티티, 속성, 범위) 키를 만들고 시간순 버전 사슬을 유지(동일 값 재확인은 새 버전 아님, 되돌림은 새 버전).
4. **렌더링**: 엔티티당 한 Hermes 항목: `Orion: API port 9090 (was 8080; staging: 8081); log retention 45 days`.
5. **예산 배치(결정적)**: 한계 글자 비용 탐욕법 — 추가 비용이 가장 작은 사실부터 넣어 B자 안에 **보존 사실 수를 최대화**(동률 시 현재값>예외>이전값>자유메모, 최근 갱신 우선; 이전 값은 현재값이 있을 때만). 넘친 사실은 보관 파일로.
- LLM이 메모리를 다시 쓰지 않으므로 예외를 기본값으로 덮거나, 옛 값을 현재값으로 남기거나, 여러 사실이 든 항목을 통째로 지우는 일이 구조적으로 불가능하다(Hermes가 `replace`를 없앤 이유와 같은 문제).

## 5. 측정
- 정확도(유형별/매크로/마이크로), 오류 유형 분포, hedge(한 답에 같은 키의 값 2개 이상).
- **저장 vs 읽기 손실 분해**: 정답 값이 해당 엔티티 항목 안에 있는가(엔티티 결합 보존) × 정답 여부.
- 추출 품질(값 재현율, 기본/예외 범위 일치율, 기각값 유입), Hermes 도구 통계(호출·실패·용량 초과 오류).
- 비용: 압축 단계 LLM 호출 수, 생성 토큰, 시간; 질의 프롬프트 토큰.
- 통계: 질문 단위 McNemar 정확검정(시드 통합) + Holm 보정, (시드, 엔티티) 군집 부트스트랩 95% CI(2,000회).

## 8. 실험 2 (추가, 16:35): Hermes 반복 문맥 압축의 누적 정보 손실
사용자 제안("동일 대화를 1·3·5·10회 압축, 원본 참조 vs 요약본 재압축, 정보 유형별 보존율·정답률·토큰")을 반영.
- **기본 압축 = Hermes 실제 문맥 압축기**: `agent/context_compressor.py`의 `ContextCompressor._build_summary_prompt`를 import하여
  그대로 사용. 첫 압축은 구조화 체크포인트 요약, 이후 압축은 **이전 요약 + 새 대화**를 갱신(PREVIOUS SUMMARY / NEW TURNS TO INCORPORATE).
  요약 예산은 Hermes 기본값(최소 2,000토큰, 출력 상한 없음 — 폭주 방지용 2,600토큰만 설정), FOCUS TOPIC 기능에 다른 방법과 같은 과제 안내를 넣음.
- 같은 메모 스트림을 k = 1, 3, 5, 10 구간으로 나눠 k번 압축(요약본만 재압축) → 최종 요약으로 같은 475개 질문에 답함.
- **원본 참조 재압축**: 매번 원본 전체를 새로 요약 — 최종 요약은 k=1과 같고, 다시 읽어야 하는 입력 토큰은 k에 비례해 증가(k=1 실측으로 추정).
- **개선 방식 = CEM 사실 원장**: 원본에서 추출한 사실 원장을 다시 렌더링하므로 k와 무관(구조적으로 누적 손실 없음). 압축 요약도 2,200자 제한이 없으므로
  CEM도 글자 제한 없이 전체 원장(약 3.5천 자)을 같은 "CONTEXT CHECKPOINT SUMMARY" 머리글로 제공(`cem_ledger`).
- 측정: k별 정확도(유형별), 엔티티 결합 보존율, **정보 유형별**(현재 설정값 / 변경 이력 / 예외 조건 / 결정(기각 후 유지) / 교훈·명령 메모, 값 종류: 수치 / 식별자 / 시각)
  정답·보존율, 압축 입력·출력 토큰, 요약 길이.
- 모델: qwen3.5:4b(시드 1–3, 두 번째 GPU 슬롯), qwen3.5:9b(시드 1–2, 시간 허용 시 3).
- 자원 재배분: gemma4:e4b 교차 모델 실험과 E=48 규모 실험은 취소(시간 부족), 예산 스윕(시드 1)과 E=12는 유지.
